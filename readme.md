# CodeCircuit 🔍

### Toward Inferring LLM-Generated Code Correctness via Attribution Graphs

> This paper conducts an in-depth investigation into a central question: ​**can code generated by LLMs be evaluated for correctness *without* relying on external assistance**​?

> Inspired by mechanistic interpretability, we conduct a series of investigations. **Our key contribution is the demonstration that internal computational structures of LLMs—neural circuits—can serve as indicators of the correctness of generated code.**

> We explore a new avenue for verification and aim to provide insights that may inspire future work, with neural circuits emerging as a direction worthy of attention.

---

# Abstract

Current paradigms for code verification rely heavily on external mechanisms—such as execution-based unit tests or auxiliary LLM judges—which are often labor-intensive or limited by the judging model's own capabilities. This raises a fundamental, yet unexplored question: Can an LLM's functional correctness be assessed purely from its internal computational structure? Our primary objective is to investigate whether the model’s neural dynamics encode internally decodable signals that are predictive of logical validity during code generation. Inspired by mechanistic interpretability, we propose to treat code verification as a mechanistic diagnostic task, mapping the model's explicit algorithmic trajectory into line-level attribution graphs. By decomposing complex residual flows, we aim to identify the structural signatures that distinguish sound reasoning from logical failure within the model’s internal circuits. Analysis across Python, C++, and Java confirms that intrinsic correctness signals are robust across diverse syntaxes. Topological features from these internal graphs predict correctness more reliably than surface heuristics and enable targeted causal interventions to fix erroneous logic. These findings establish internal introspection as a decodable property for verifying generated code.

# Replication log (this fork)

This fork replicates CodeCircuit on Python and extends it to Rust in eight
phases: reproduce the Python number (finished 2026-09-16); ask the same question
of Rust under a pre-registration (`PREREGISTRATION.md`, finished 2026-10-01);
ask it within a problem, on two solutions to the same task
(`PREREGISTRATION_WITHIN.md`, finished 2026-10-02); ask it at identical
length, on two one-token mutants of one passing solution
(`PREREGISTRATION_MUTANT.md`, finished 2026-10-08); ask it again with the
model's surprise matched as well (`PREREGISTRATION_MATCHED.md`, finished
2026-10-12); try it on the model's own errors and their one-token repairs
(`PREREGISTRATION_OWNFIX.md`, stopped at its gate 2026-10-13); compare the
graph, on Phase 5's retained pairs, with cheap signals and a probe of the same
forward pass (`PREREGISTRATION_CLOSING.md`, finished 2026-10-14); and test the
paper's causal claim by zeroing graph-ranked features at the model's own bugs
(`PREREGISTRATION_P8_INTERVENTION.md`, finished 2026-10-19). The study closed
with Phase 8; the conclusion comes first, the phases follow.

## Conclusion (study closed 2026-10-19)

No further phase is planned. Over eight phases, seven of them pre-registered,
the study built 4,349 attribution graphs. Its answer to each of the paper's
claims, measured against execution at the problem level unless noted
(intervals are 95% and resample problems):

| the paper's claim | answer here | phases |
|---|---|---|
| Graph features predict whether LLM-generated code is correct (AUROC 79.89%, Python) | **The number reproduces** on the paper's protocol (79.73%). That protocol scores rows against an LLM judge whose prompt sets the shape of the labels. Against execution, per problem and under the same 140-token cap: 0.727 [0.662, 0.790] in Python, 0.789 [0.725, 0.848] in Rust | 1, 2 |
| They do so line by line | **Cannot be tested on the shipped labels.** One cutoff per problem rebuilds 1418 of their 1420 rows, and within a problem the line's position alone scores 0.998 (the trained model 0.885) | 1 |
| They beat the paper's surface baselines, output-probability scores such as MaxProb, perplexity and entropy | **Not shown here.** Between problems those baselines were not rerun; there the graph beats length and size heuristics, which are not among the paper's baselines: +0.103 [+0.041, +0.166] in Python, +0.094 [+0.025, +0.165] in Rust. Within pairs, the output distribution (code and edit-token log-probabilities, entropy, the final position's top probability) separates the members as well as the graph (Phases 4, 5), and added to it and the kind of edit, the graph gives +0.002 [−0.072, +0.074] (Phase 7) | 1, 2, 4, 5, 7 |
| They read the model's computation on the code it wrote, "sound reasoning" against "logical failure" | **Not shown beyond cheaper signals.** In Python the code adds nothing measurable over the signature (+0.034 [−0.016, +0.085]). In Rust it adds, but not separably from length (Phases 2–3). At identical length the registered test is null (0.469), and the within-pair signal (0.674) cannot be separated from the model's surprise. With surprise matched as well, the graph separates the pair (0.641, p 0.004), but the kind of edit alone does as well (0.676), and the graph adds nothing measurable to the cheap signals (the row above) | 1–5, 7 |
| The attribution is what carries the signal | **Not shown beyond plain activations.** Inside the graph, the attribution-dependent columns carry most of the 0.641: the three attribution-free features alone score 0.541 (difference +0.100 [+0.000, +0.200], undecided as published, above 0 without the erratum's pair). But a probe of plain transcoder activations, with no attribution, scores 0.685, and given the kind of edit, the output distribution and the active-feature count, the one valid test of attribution does not reject (p 0.024 against Holm's 0.0167) | 7 |
| The signal holds across languages (Python, C++ and Java in the paper) | **Partly.** The graph beats length heuristics in Python and Rust alike, but whether the code contributes differs between the arms, and the arms differ in more than language. C++, Java and cross-language transfer were not run | 1, 2 |
| Zeroing a feature picked from the graph fixes a bug (§4.4, one case) | **The features are causal; as a repair, the graph does worse than a token ban.** At 142 sites of Gemma's own one-token bugs, zeroing the graph's top features cumulatively (median 20) changes the model's choice at 91% of sites (matched random features: 10%) and repairs 0.34 (random: 0.05). Forbidding the wrong token repairs 0.56 (graph − ban −0.224 [−0.369, −0.086]) and gradient × activation 0.40; 48 of the graph's 57 repairs are the token the ban gives. The graph's single top feature changes the choice at 4% of sites | 8 |

In short, the attribution graph carries real information about whether the code
works, and the features it ranks highest do drive the model's choice. It beats
length and size heuristics between problems (Phases 1–2). But wherever it was
set against a cheaper method (Phases 4, 5, 7 and 8), it did no better: the kind
of edit, the output distribution, a probe of plain activations, a token ban, or
one backward pass.

**What the study does not cover.**
- One model, gemma-2-2b-it, with its transcoders; MBPP's short functions;
  Python and Rust only.
- Phases 4–8 work with one-token edits. Phase 6, which would have used the
  model's own errors as prediction targets, stopped at its gate.
- Four of Phase 7's five tests were withdrawn by their size check, and the
  graph's increment over the cheap signals does not exclude a gain of up to
  0.07.
- Phase 8 starts from a one-token bug at a known position, where a ban exists.
  It does not find bugs.

**What would reopen it.**
- New problems, enough for a valid test of the graph's increment over the kind
  of edit, the output distribution and a probe. Phase 7 reused Phase 5's pairs.
- A larger model, or cross-layer transcoders.
- Bugs longer than one token, where forbidding one token may not be enough.
  That is where a graph-guided intervention could still beat a cheap one.

## The eight phases in brief

The paper's number reproduces — 79.73% against 79.89% — but it is a row-level
score against an LLM judge whose prompt dictates the shape of the label. Measured
at the problem level against execution, with intervals that resample problems,
the graph features still beat surface heuristics in both languages; that much of
the paper survives. The sharper question is whether the *generated code*
contributes anything beyond the prompt, and there the two arms differ. In Python
it does not: a graph taken at the signature, before a line of logic exists,
predicts execution as well as one over the whole function, while the body does
help predict what the judge will say. In Rust it does — between problems, and
weakly between two solutions to the same problem — but in both designs that
contribution cannot be separated from the code's length at this n. The arms
differ in more than language (the Python labels lean on name-aliasing for 99 of
114 positives; the Rust prompt carries the signature), so the difference is not
attributed to language. Phase 4
removes length by construction, pairing two one-token mutants of one passing
solution at identical length, and the pre-registered test detects nothing.
Compared within each pair (exploratory), the graph features do tell the passing
copy from the broken one, but the model's own surprise at the edit does so at
least as well, and with that surprise removed (post hoc) the graph's separation
is no longer significant; the kind of edit alone separates the pair as well
(post hoc). Phase 5 matches the members on surprise by design as well, and
there the graph features do separate them (0.64, p 0.004, and 0.64 with the
remaining surprise removed). But the rest of the model's output distribution
separates them as well (0.65), and the kind of edit at least as well (0.68), with the
graph adding nothing measurable to it. In Rust, then, the graph carries
information about correctness, but it has not been shown to carry information
that cheaper signals lack. Phase 6 tried to settle this on Gemma's own errors, a
verified one-token repair against a control of the same code, and stopped at
its pre-registered gate: about half of the repairs that pass MBPP's asserts are
wrong on nearby inputs, and only 20 clean pairs could be built. Phase 7 asked
the question directly on Phase 5's pairs. Given the kind of edit and the output
distribution (0.71), the graph's 49 features add nothing (+0.00 [−0.07, +0.07]
after correcting for dilution). A probe of plain transcoder activations, with no
attribution, does as well as the graph (0.69 against 0.64). A third of the
checkable surviving mutants (64 of 193) turn out wrong on extra inputs, and the graph, the cheap
baseline and the probe all rank those pairs near chance: they track whether the
program still works, not whether it passed three asserts.

Phase 8 tested the paper's other claim, that zeroing features the graph picks
can fix a bug. At 142 sites of Gemma's own one-token bugs (92 distinct bugs, 30
problems), zeroing the graph's
top-ranked features changes the model's choice at 91% of sites, where matched
random features do so at 10%, and repairs 34% of them (equal weight over
problems). Forbidding the wrong token repairs 56%. Most of the graph's repairs
are the token the ban gives anyway; where the ablation sends the model
elsewhere, the code usually breaks. Gradient × activation, without the graph,
does as well as the graph. For prediction and for repair alike, the graph is
not shown to do more than cheap methods.

## Phase 1: the Python arm

| Split | AUROC | vs. paper (79.89%) |
|---|---|---|
| Ordered 70/30, as in `5_classification.py` | **79.73%** | −0.16 pt |
| `GroupShuffleSplit` by `expr_id`, 20 seeds | 77.06% ± 4.25% | −2.83 pt |

Both numbers come from the same 1420-graph dataset (248 label-0, 1172 label-1,
256 problems; no graph failed or was skipped).

**The ± above is not a confidence interval, and neither is any other ± in the
literature this replicates.** Twenty `GroupShuffleSplit` seeds reshuffle splits
of the *same* 256 problems, so the spread measures split noise, not sampling
error. Resampling the 256 problems instead gives intervals 4–10× wider. Every
interval below is a cluster bootstrap over problems. For the same reason, a
paired t or Wilcoxon over seeds is not a hypothesis test: its p-value is a
function of how many seeds you draw — `-max prefix chars` against `-n_steps`, a
true gap of +0.0216, gives p = 0.0020 at 10 seeds, 0.0001 at 20 and below 0.0001
at 30. (An earlier version quoted 0.2305 / 0.0494 / 0.0010 at 20 / 50 / 100
seeds; that triple does not reproduce from anything recorded and is withdrawn,
`PREREGISTRATION.md` §2.)

**Two corrections to earlier versions of this section.** First, the gap between
the two splits was described here as train/test leakage. It is not. Exactly 1 of
256 problems straddles the positional boundary (task 392, 1 row in train and 13
in test = 3.0% of ordered test rows), and a task-identity oracle scores AUROC
0.4933 on that split — chance. The gap is which problems landed in test. (The
straddle is a real if minor defect in the paper's protocol, so the ordered
numbers should be read as confirmed by the grouped ones rather than standalone.)

Second, this section previously argued that re-labelling against execution
"drops" AUROC from 0.7973 to 0.6068 and that this indicts the paper. That
framing was wrong twice over. The execution labels had a bug of my own (below),
and the comparison was made at row level against a task-constant label, which
weights each problem by its solution length — and length correlates with the
label. Corrected and measured at the problem level, the paper's central claim
survives; its headline magnitude and its reported precision do not.

### What the 79.73% measures

The labels are not execution results. `1_code_correct.py` asks gpt-4o-mini to
score each generated line 1 or 0, and its prompt *mandates* the shape the labels
come out in:

> Once a line violates the requirements, all following lines must also be 0.

So the label is not an emergent judgment about each line. It is one cutoff index
per problem, by construction. What follows is measured on this dataset:

- **256 integers reproduce the whole label set.** 255 of 256 problems have
  monotone non-increasing scores (the exception is task 172, `[1,1,1,0,1,1]`).
  Predicting "1 iff `step_number` < cutoff" reconstructs 1418 of 1420 row labels
  — 99.86%. The 1420-row vector carries at most 625.25 bits (Σ log₂(nᵢ+1)).
- **Effective sample size is 256 problems.** ICC of the judge label is 0.4976
  (n_eff ≈ 435 rows); for a task-constant execution label ICC is 1 by
  construction and n_eff is exactly 256. This does not move the point estimate —
  it inflates precision, by 1.95× on identical predictions.
- **A second prompt rule explains the judge's blind spot.** Rule 4 tells it to
  ignore "parameter variable names, function names, and so on". MBPP never states
  the required function name, so 210 of 256 generations fail execution on
  `NameError` — the one failure mode the judge is instructed not to look at.
- **The signal is between problems, not within them.** Only ~1% of (positive,
  negative) test pairs are within-task, and deleting every within-task comparison
  moves the row-level judge AUROC by −0.0010. The within-task signal that does
  exist is positional: untrained `-step_number` scores 0.9976 on same-task pairs
  against 0.8850 for the trained 49-dim model. This dataset cannot evidence
  line-level error localisation for any method, in either direction.

### Against execution instead

MBPP ships tests. Running the 256 generations against them (subprocess, 10 s
timeout) re-labels the *same* graphs — only `y` changes, so the 5 days of graph
compute is reused.

**A bug of mine, found independently by two analysts.** My first execution labels
never ran MBPP's `test_imports`, so the 13 problems whose asserts call
`math.isclose` failed spuriously. The aliasing rule, stated in full because an
earlier version of it was not: take the first `Call` in the assert whose func is
a bare `Name`, in source order, preferring a name not in `builtins`; if every
candidate is a builtin take the first anyway (task 126 genuinely tests a function
named `sum` — this fallback fires exactly once, and it is the whole 113-vs-114
discrepancy between two independent reimplementations); if the generation defines
exactly one top-level function under a different name, bind the target to it.

| Target | pass rate | problem-level AUROC | 95% CI (bootstrap over problems) |
|---|---|---|---|
| Execution, name-adapted | 114/256 (44.5%) | **0.7324** | [0.6703, 0.7918] |
| Execution, strict | 15/256 (5.9%) | 0.6234 | [0.4445, 0.7919] |

The paper's 79.89% lies outside that interval. Strict execution is unusable as a
target: 15 positives, and an interval that includes chance.

Judge and execution disagree on 47% of rows, one-directionally — **69 problems
where the judge passes a failing solution against 6 the other way** (κ = 0.44).
Of those 69, 58% return a wrong value of the right type and only 6 pass the first
assert and fail a later one: they are wrong algorithms, not edge cases. The 6 in
the other direction are all working code that diverged from MBPP's idiom
(`int(a/b)` where the reference uses `//`, a comprehension where it uses `map`).

One caution on the sensitivity analysis: AUROC across eight execution-label
variants is perfectly rank-ordered by positive rate (Spearman = 1.00, n = 8), so
label-definition effects and base-rate effects cannot be separated here.

### What survives, and what does not

**Survives — the paper's comparative claim.** At the problem level against
corrected execution labels, the graph features beat surface heuristics by a
margin whose bootstrap CI excludes zero. Four independent implementations agree
on the direction and roughly on the size:

| Comparison | Δ AUROC | 95% CI |
|---|---|---|
| 49 graph dims vs trained RF on 14 surface features | +0.1519 | [+0.0737, +0.2302] |
| 49 graph dims vs `-n_steps` | +0.1310 | [+0.0641, +0.1988] |
| 49 graph dims vs `-len(generated_code)` | +0.1032 | [+0.0384, +0.1669] |

This margin is the number that reverses if you score at row level, because a
row-level AUROC against a task-constant label weights each problem by its
solution length, and length correlates with the label. Measured at row level the
same comparison looks like a tie; that appearance is a metric artefact.

**Survives — the features are not a size proxy.** Ten of the 49 dimensions
correlate |r| > 0.7 with prefix length, `total_active_features` reaching 0.974.
Dropping all ten costs 0.009 (0.7324 → 0.7232 [0.6604, 0.7820]). That most
length-correlated dimension, used alone, scores 0.5329 [0.4590, 0.6036] — chance.

**Does not survive — the magnitude.** 0.7973 is a row-level score against a
prompt-mandated step function. The comparable quantity is 0.7324 [0.6703, 0.7918].

**Does not survive — the reported precision.** See the note on ± above.

**Open, and the most interesting thing here.** The dimensions carrying the
execution signal are not the ones carrying the judge signal: Spearman between the
two permutation-importance vectors is 0.031, sharing 2 of 10 top dimensions.

### The sharpest Python result: the features read the judge, not the execution

Found by red-teaming the Rust pre-registration before the Rust data existed, and
confirmed by re-running it. `original_expression` — what the graph is computed on
— is the prompt plus a code prefix, and at step 0 that prefix is one line: the
function signature. No body. No logic that could be right or wrong. Comparing a
model trained on all rows against one trained on step-0 rows alone isolates what
the generated body contributes.

| target | all rows | step-0 only | contribution of the body |
|---|---|---|---|
| gpt-4o-mini judge, all lines 1 | 0.6992 | 0.6114 | **+0.0882 [+0.024, +0.154]** |
| judge, majority of lines | 0.6811 | 0.5685 | +0.1134 [−0.009, +0.244] |
| **execution truth** | 0.7269 | 0.6931 | **+0.0340 [−0.0160, +0.0846]** |

Read carefully, because the two rows say different things.

**Against the judge, the body does contribute** — the interval excludes zero.
That is not surprising once stated: the judge reads the code, so predicting the
judge benefits from seeing the code.

**Against execution truth it does not.** A graph taken before the model writes a
line of logic predicts whether the program actually works as well as one taken
over the whole generation. On the clean 240-problem subset the contrast shrinks
further, to +0.0165 [−0.0341, +0.0684], and with the 16 corrupted generations
repaired and their graphs rebuilt (2026-10-01) it is +0.0162 [−0.0352, +0.0691].

So the honest statement is narrower than "it is all problem difficulty", and
more specific: **the features carry information about what an LLM judge will say
about the code, and no separable information about whether the code runs.** The
part of the signal that predicts execution is not distinguishable from a read on
problem difficulty, which is available before the answer exists.

The rest of the dataset agrees that correctness here is largely a property of the
problem: on the 129 problems both arms share, copying the Python label predicts
Rust correctness at **AUROC 0.8669** (86.0% agreement, φ = +0.731).

This is why the Rust arm's primary result is the paired contrast rather than the
AUROC — see `PREREGISTRATION.md`. The features do beat surface length heuristics
(+0.1026 [+0.0408, +0.1658]), and that survives; what does not survive is reading
the headline as evidence about generated code rather than about the problem.
Rust answered the same contrast differently; see Phase 2.

### Known defects in this dataset

- **16 of 256 generations carry markdown fences.** `generated_code` contains
  literal ``` fences and, in several cases, the same functions repeated several
  times — an extraction bug upstream of everything here, not a model failure.
  They account for 242 of 1420 rows (17%), and the judge scored every line 1 on
  6 of them, including the bare fence line, against its own rule 1. Predicting
  "does this parse" from the graph features scores **0.9995** [0.9975, 1.0000]
  at problem level: these features separate sharply when the target is an
  extraction artefact, and weakly when it is correctness. Repaired on
  2026-10-01 into separate `*_repaired` files, the locked originals untouched;
  the Python C1 stays null (Phase 2, "The Python top-up").
- **The `len(text) > 550` filter is class-biased.** 27 of 1447 rows dropped, 67%
  of them label 0 against a 17.5% base rate. Six of the eight affected problems
  are the fence-corrupted ones.
- **The study is data-starved.** The learning curve is still rising at the
  largest training set available: 51 problems → 0.663, 102 → 0.715, 153 → 0.733,
  204 → 0.752. 256 problems does not saturate this question.
- **Three of the 49 features are constant** — `n_connected_components` (always 1)
  and both shortest-path dimensions, stuck at their −1.0 sentinel because
  `adjacency_matrix` never populates input-token rows. The effective feature
  space is 46-dimensional.

**`BATCH_SIZE` is not a performance knob**, which matters before comparing across
languages. `attribute()` chooses which `MAX_FEATURE_NODES` of the active features
enter the graph by greedy frontier expansion, re-ranking once per
`update_interval * batch_size` features, so it changes the graph itself. The cap
binds on **all 1420 graphs** — active feature counts run 16,785 to 216,132
(p5–p95: 27k–152k), so 8192 is between 3.8% and 48.8% of what was available, and
never more than all of it. All 1420 graphs were generated at the upstream default
of 64, and the Rust arm used the same value, as did every later phase that built
graphs.

## Plan for the Rust arm

*Written before any Rust graph existed and kept as written; where the plan
changed, `PREREGISTRATION.md` §8 records it.*

The Python arm's real finding is not "the paper is wrong" — its comparative claim
held up under adversarial checking. It is that the reported quantity is measured
at the wrong unit, against a target whose shape a prompt dictates, with intervals
that understate uncertainty several-fold. The Rust arm is worth running as the
same question asked properly, and it must not repeat any of this.

1. **Fix the extraction before generating anything — done.**
   `0_generate_responses.py` now treats fences as separators rather than
   delimiters (pairing is what broke: the model emits ``` immediately followed
   by ```python, and a paired regex reads the second as the first's closing
   fence and drops everything outside), de-duplicates repeated blocks, drops a
   block that a later one restarts, and preserves indentation so a fence that
   splits a `def` from its body rejoins. It then refuses to finish quietly:
   every generation is `ast.parse`-checked and the failures are listed. Applied
   to the shipped Python generations the new extractor repairs **16 of 16** and
   changes none of the 240 that already parsed — it would take the parse rate
   from 240/256 to 256/256. The same fix went into the Java script; the C++
   script already had a working version further down the file, shadowing the
   broken one, which is where all three copies most likely came from. That dead
   copy is deleted.

   **Correction.** An earlier version of this line said "parse rate 240/256 →
   256/256" as though the data had been repaired. It has not. The fix landed in
   the script only: `data/gemma_mbpp_responses.jsonl` is still the pre-fix file,
   16 generations still fail `ast.parse`, and 147 of the 1420 feature rows
   contain a literal ` ``` `. Repairing it meant regenerating those 16 problems'
   graphs, which had to wait for the Rust run, so the like-for-like comparator
   was locked in `PREREGISTRATION.md` §3b as the 240 problems that parse, before
   any Rust number existed: 0.7091 [0.6402, 0.7737] against 0.7269 [0.6619,
   0.7901] on all 256. The repair landed on 2026-10-01 in separate `*_repaired`
   files (Phase 2, "The Python top-up").
2. **Put the required signature in the generation prompt.** MBPP does not state
   the function name, which cost 210 of 256 Python generations a `NameError`
   before any assert ran. Ported naively that becomes a Rust compile error, and
   the label measures naming rather than reasoning.
3. **Label with `cargo test`, not an LLM judge**, and re-label the Python arm the
   same way so the two are the same quantity. Graphs are label-independent, so
   each re-labelling costs seconds rather than another 5-day run.
4. **Evaluate at the problem level, with a bootstrap over problems.** Execution
   labels are constant within a problem, so a row-level AUROC weights problems by
   solution length and a seed-to-seed sd measures split noise rather than
   sampling error. Score one aggregated prediction per held-out problem and
   resample problems for every interval. Do not report a paired t or Wilcoxon
   over splits: its p-value is a function of the seed count, not of the evidence.
5. **Pre-register the comparison as 0.7324, 95% CI [0.6703, 0.7918].** That is
   Python at the problem level against corrected execution truth. Comparing Rust
   to 79.89% compares two different quantities measured two different ways.
6. **Use more than 256 problems.** The Python learning curve is still rising at
   204 training problems, and the interval on any single label definition is
   ±0.06. At this n, a Python-vs-Rust difference smaller than about 0.10 is not
   resolvable, so a null result would be uninformative rather than interesting.
7. **Match the length filter on tokens or on drop rate**, and report the dropped
   count and class balance per language. A fixed character threshold will cut a
   different share of a more verbose language.

### Setup

Everything below was done before any graph was built, to find out whether the
arm was viable before committing GPU time.

**How much of MBPP can be ported.** `data/mbpp_rust.py` reads a Rust signature
off the literals in each task's asserts, requiring the types to agree across
every assert and rejecting the task rather than guessing when they do not.
**350 of 427 tasks survive (82.0%)**; of the Python arm's 256, 207 do. The
rejects are 31 whose argument types disagree between asserts, 18 with an
argument type that has no simple Rust form (empty list literals, dicts, None),
13 with disagreeing return types, 10 with an unrepresentable return, and 5 with
a non-literal argument. Returns are 153 `i64`, 55 `bool`, 40 `Vec<i64>`, 34
`String`, 21 `f64` and a tail of tuples; 237 of the 350 take one argument.

**Labels come from `rustc`, not a judge.** `data/1_rust_correct.py` compiles each
generation, renames any `main` the model wrote, evaluates every assert inside
`catch_unwind` so a panic in case 2 cannot hide that case 1 passed, and runs
under a wall-clock timeout. Float asserts use MBPP's own `rel_tol=0.001`. It is
checked against eight hand-written solutions whose outcomes were stated in
advance — correct, wrong answer, syntax error, type error, panic, infinite loop,
a solution defining its own `main`, one defining a helper — and classifies all
eight as specified.

| | Rust | Python (same protocol) |
|---|---|---|
| compiles / parses | 214/350 (61.1%) | 256/256 after the extraction fix |
| passes every assert | **99/350 (28.3%)** | 114/256 (44.5%) |
| passes, given it compiles | 99/214 (46.3%) | — |

On the 207 problems both arms can express: Python passes 97 (46.9%), Rust 55
(26.6%); 51 pass in both, 106 in neither, 46 in Python only and **4 in Rust

**Two pipeline artefacts, found before spending GPU time.** The Python arm's

dangling signature the prompt ends on — and 9 ended with unbalanced braces
because the model finished the function, started rewriting it, and hit the token

## Phase 3: two solutions to the same problem

Phase 2's contrasts compare problems with problems, so problem difficulty and
length are controlled only statistically. Phase 3 controls them by design: draw
many solutions per problem and pair one that passes with one that fails, both
compiling, matched on length. Problem difficulty cannot help a classifier tell
the members of a pair apart, and length can help only through what the matching
left. Pre-registered in `PREREGISTRATION_WITHIN.md`: version 1 before any sample
was drawn, version 2 after a yield pilot that saw labels only — never a graph —
and before the real draw (§8 records the change and the numbers it was decided
on).

**Design.** The 334 Rust problems whose every assert is gradeable, 20 samples
each at temperature 0.8 (top_p 0.95), with the Phase 2 prompt and extraction plus
a cleaner for wrapping debris (`data/within_clean.py`). A sample is eligible if
it compiles, is not truncated, and fits prompt plus whole solution into 140
tokens, so the graph sees the complete function. Each problem gives at most one
pair: the passing × failing combination with the smallest token difference.
Every sample gets its own graph through the Phase 2 pipeline and the same 49
features. The classifier is Phase 2's random forest, with folds grouped by
problem so a pair is never split, and the statistic is **A**: the fraction of
pairs whose passing member scores higher, tested against 100 refits with each
pair's labels swapped at random.

**The draw.** 6680 samples; 56.3% compile, 24.9% pass. 89 problems yield a pair
(gate: 70). Every failing member fails an assertion and none timed out; the
absolute token difference within a pair has median 2 (signed mean +0.00). 178 graphs, none
missing (2026-10-01 13:42 to 10-02 20:31).

| | A | 95% CI | label-swap p |
|---|---|---|---|
| **graph features (primary)** | **0.624** | [0.522, 0.719] | **0.020** |
| S1: features residualised on length | 0.534 | [0.427, 0.635] | 0.267 |
| S2: length alone | 0.545 | [0.444, 0.646] | — |
| per-feature paired tests, BH q < 0.1 | 0 of 49 | | |

My prediction — A's p above 0.05 — failed; S2's (near 0.5) held. By the
pre-registered table this reads: **a within-problem signal that cannot be
separated from the length difference matching left.** It is weak: 89 pairs
resolve A ≈ 0.63 at 80% power, and the interval's lower end is 0.52.

**What did the length correction remove?** (Exploratory:
`8_within_length_decomposition.py`, committed with its reading rule before it
ran.) The members' lengths are nearly equal and unsigned, yet S1 removed most of
A. S1's pooled fit removes two things at once, so each was removed alone:

| removed | A | 95% CI | p |
|---|---|---|---|
| nothing | 0.624 | [0.522, 0.719] | 0.020 |
| E1: each member's length departure from its pair's mean | 0.590 | [0.489, 0.697] | 0.059 |
| E2: the pair's mean length among problems (within-pair differences unchanged) | 0.567 | [0.466, 0.663] | 0.158 |
| both (S1) | 0.534 | [0.427, 0.635] | 0.267 |

No clean split: of the 0.090 that S1 removed, E1 alone removes 0.034 and E2
alone 0.056, and both, like the 0.022 between them, are smaller than one null
sd (0.060–0.066), so 89 pairs cannot apportion the drop. The data lean towards
the members' own length difference not being most of the signal — removing it
leaves 0.590 — but a lean is all it is. Length still reaches the features:
feature by feature, it explains a median of 10.5% of the within-pair variance
(IQR 5.4–16.0%), although the members differ by a median of two tokens. (An
earlier version said 31%; that figure pooled raw-scale sums of squares, 98.9%
of which belong to a single feature.)

**Limits.** The random forest dilutes a signal carried by one feature: on 40
synthetic pairs with one of 49 features shifted by 1.5 SD — a feature that
alone would rank about 86% of pairs correctly — it reached A = 0.625. Only
problems the model sometimes solves can form a pair, so the population is the
model's frontier; the solutions are sampled, not the greedy ones Phase 2
graphed; and the 140-token cap keeps only short functions.

## Phase 4: one-token mutants at identical length

Phase 3's signal could not be separated from length: two solutions with the
same token count still differ in many places, and length reaches the features
anyway. Phase 4 removes the length difference by construction. It takes one
passing Phase 3 solution per problem and changes a single token — a comparison,
arithmetic, compound-assignment, logical or boolean operator, an integer
literal 0, 1 or 2, or a range operator — keeping Gemma's token count exactly
equal. A pair is one mutant that still passes every assert (the *survivor*) and
one that fails (the *killed* mutant). Pre-registered in
`PREREGISTRATION_MUTANT.md` before any mutant was generated; the pairs were
committed before any graph was built, and the rules for reading the secondary
analyses before any feature existed (§8).

```rust
// task 309, "find the maximum of two numbers": the line each mutant changes in
// `if a0 > a1 { a0 } else { a1 }`; both members are 62 tokens with the prompt
  if a0 >= a1 {   // survivor: `>` -> `>=`, passes 3 of 3 asserts
  if a0 <= a1 {   // killed:   `>` -> `<=`, returns the minimum
```

**Design.** 4563 mutants judged; 4518 compile, 317 survive, 4201 are killed.
99 problems yield a pair (gate: 70); in 89 the two edits come from the same
family, in 57 they sit on the same token. Each member gets its own graph and
the same 49 features. A is Phase 3's statistic and test, unchanged. S1 removes
the model's *surprise* at the edit — the within-pair differences in the code's
log-probability and characters — by a fit inside each pair; S2 is the surprise
alone. One graph, the killed member of task 633, twice raised a CUDA error, the
first time followed by a crash of the PC, and was given up, so 98 pairs were
analysed. The run took from 2026-10-04 16:00 to 10-08 00:44, with the PC down
from 10-05 16:47 to 10-07 15:34.

| | A | 95% CI | label-swap p |
|---|---|---|---|
| **graph features (primary)** | **0.469** | [0.367, 0.571] | **0.723** |
| S1: within-pair surprise removed | 0.490 | [0.388, 0.592] | 0.683 |
| S2: surprise alone | 0.551 | [0.454, 0.648] | 0.238 |
| per-feature paired tests, BH q < 0.1 | 21 of 49 | | |
| *exploratory* Ac: graph features centred within each pair | 0.674 | [0.582, 0.765] | 0.010 |
| *exploratory* S2c: surprise centred within each pair | 0.694 | [0.602, 0.786] | 0.010 |
| *post hoc* S1c: centred, within-pair surprise removed | 0.592 | [0.490, 0.684] | 0.139 |

My prediction for A — p above 0.05 — held, the first of my four predicted
nulls to do so. By the pre-registered table this reads: **not detectable at
this n, which is not evidence of absence**; 98 pairs resolve A ≈ 0.63 at 80%
power (≈ 0.65 by the null's own spread), and the interval's upper end, 0.571,
lies below Phase 3's 0.62. The prediction for surprise held in
part: the killed mutant is the less probable one in 70 of 98 pairs (Wilcoxon
p 2 × 10⁻⁵), but S2's forest does not turn that into a significant ranking.

**Why the primary test missed what the paired tests see.** 21 of the 49
features differ between survivor and killed mutant, nearly all in one
direction: the killed mutant's pruned graph is larger, with more feature nodes
(in 74% of pairs), error nodes and edges. The forest is fed levels, and levels
vary far more between problems than a one-token edit moves them. An audit
before the analysis showed this on synthetic pairs (A 0.52 on levels, 0.91 on
the same values centred within each pair), and a centred version was committed
as exploratory before any result existed (`m4_mutant_centred.py`). Centred,
the graph features rank the survivor higher in 67% of pairs and the model's
surprise in 69%; none of the 100 label-swap refits reached either.

**Is it more than surprise?** The graph differences track the model's
surprise: the less probable the killed mutant, the larger its graph (Spearman
−0.34 to −0.49 for those three). A post-hoc analysis, committed with
its reading rule before it ran (`m5_mutant_posthoc.py`), removes the
within-pair surprise from the centred features, and A falls from 0.674 to
0.592 (p 0.139). At this n, the graph's within-pair signal **cannot be
separated from the model's surprise at the edit**. That is not evidence that
the graph reads only surprise — the correction is linear and also strips about
a sixth of any difference unrelated to surprise — but nothing here shows that
it reads more. A fresh draw, pre-registered with this statistic as its
primary, could.

**Or more than the kind of edit?** Found later, while preparing Phase 5, and
post hoc here: the two members carry different edits, and the edit's surface
identity alone — which token was replaced, by which, and where — ranks the
survivor higher in 0.667 of all 99 pairs (p 0.005, `p5_5_edit_baseline.py`; it
needs no graph, so task 633's pair is included). On the 98 analysed pairs it
scores 0.643, about as often as the graph features' 0.674 (difference +0.031
[−0.102, +0.163]). A boundary change such as `>` → `>=` is often
harmless. Adding the graph features to the edit identity changes A by +0.036
[−0.097, +0.168]. So Phase 4's centred graph signal is not shown to exceed the
kind of edit either.

**Limits.** The mutants are not the model's own errors, and they are minimal
ones. "Survives" means passes MBPP's asserts, not "is correct": task 404's
survivor (`a0 != a1` in place of `a0 < a1`, "find the minimum") returns the
larger number whenever it comes first, which the asserts never try. The
centred results are exploratory, the post-hoc one more so; relying on them
needs a fresh, pre-registered draw.

## Phase 5: surprise matched as well

Phase 4 left open whether the graph's within-pair signal is more than the
model's surprise at the edit. Phase 5 removes surprise by design, as Phase 4
removed length. For each passing source, it takes the survivor and the killed
mutant whose code log-probabilities are closest, at most 1 nat apart, and keeps
at most 5 pairs per problem. Pre-registered in `PREREGISTRATION_MATCHED.md`
before any sample was drawn; the pairs, with every judged mutant and
log-probability, were committed before any graph was built.

**Design.** 1006 sources (Phase 3's samples and one further round of 20 per
problem), 461 usable, **259 pairs over 78 problems**. The median gap in code
log-probability is 0.18 nats, against Phase 4's 5. Graphs ran from 10-08 to
10-12; all 518 were built.

| | A | 95% CI | label-swap p |
|---|---|---|---|
| **Ac: graph features centred within each pair (primary)** | **0.641** | [0.562, 0.717] | **0.004** |
| S2c: code log-probability and characters (matching check) | 0.591 | [0.526, 0.653] | 0.005 |
| S1c: Ac with the remaining surprise removed | 0.639 | [0.568, 0.710] | 0.005 |
| S2+c: the output distribution (edit-token and lowest log-probability, entropy) | 0.649 | [0.584, 0.710] | 0.005 |
| *exploratory* E: the kind of edit alone, no model | 0.676 | [0.603, 0.743] | 0.005 |
| *exploratory* graph features added to E | 0.687 | +0.012 [−0.074, +0.098] over E | |

My prediction — Ac's p above 0.05 — failed, in the paper's favour. The
matching left a residue a forest can use: the killed member is the less
probable one in 56% of pairs, by a fraction of a nat, and the survivor is a
character longer more often than shorter. So by the pre-registered table S1c is
read in Ac's place. It removes the remaining surprise, absorbs almost nothing
(f = 0.011) and stays at 0.639, p 0.005: **at identical length, the graph tells
a passing one-token mutant from a failing one beyond the code's log-probability.**
The failing one's graph is larger: more pruned feature nodes in 60% of pairs
(p 2 × 10⁻⁷; 45 problems against 21).

**But not beyond cheaper signals.** The rest of the model's output distribution
separates the same pairs as well (0.649), and the kind of edit, with no model at
all, at least as well (0.676; graph − edit −0.035 [−0.126, +0.055]). Adding the
graph features to the kind of edit gains
+0.012 [−0.074, +0.098]. The graph carries information about these injected
errors; it is not shown to carry information that the output distribution or
the edit's surface identity lack.

**Limits.** The errors are injected one-token mutants, not the model's own, and
the population is the plausible-looking ones the matching selects. 32 of the 78
problems hold the cap of 5 pairs. The comparisons with E and S2+c are
descriptive, not tests of a difference.

## Phase 6: the model's own errors (stopped at the gate)

Phases 4 and 5 used injected errors, and Phase 5's graph-size difference had two
readings: the failing member was both the incorrect one and the one whose edit
changed the program's behaviour. Phase 6 pulled them apart with errors Gemma
made itself. From a failing solution S that Gemma wrote, R replaces one token so
that S passes every assert and a set of calibrated extra inputs; C replaces one
other token and returns exactly S's value on every assert, so it keeps Gemma's
bug. Both are matched on surprise. If the graph reads correctness, R's graph
should be the smaller; if it reads whether an edit mattered, R's should be the
larger. Pre-registered in `PREREGISTRATION_OWNFIX.md` (two adversarial reviews
worked in), with a gate of 150 pairs over 50 problems.

**Result: the gate was missed, so no graph was built.** Over Phase 3's samples
and eight further rounds of 20 per problem, 7691 failing solutions; 525 of them,
over 78 problems, are one token from passing the asserts (1371 repairs). But of
the 579 repairs that could be checked on the extra inputs, **275 (47%) passed
the asserts by luck** and returned a wrong value on a nearby input; 792 could not
be checked at all (no passing Gemma sample, or too few usable inputs). With a
control that keeps the bug, sits on a live site and matches the repair's length,
kind of edit and surprise, 20 pairs remained (49 with the fallback). Relaxing the
rules after the fact reaches 150 pairs only by admitting unverifiable repairs,
taking the fallback control and widening the surprise caliper from 1.0 to 3.0
(`data/results/ownfix/yield_whatif.log`).

So at this scale, Phase 6's question — whether the graph reads the correctness
of the model's own errors beyond cheaper signals — cannot be answered this way,
and the strong form of the claim stays unsupported in Rust. Two side results:
MBPP's few asserts often accept a wrong one-token repair; and, post hoc on
Phase 5's injected errors, graph size still differs beyond a linear adjustment
for surprise and the kind of edit (β = −0.46, CR2 95% [−0.90, −0.02], p 0.039),
a lead rather than a finding.

## Phase 7: the closing comparison

Phase 5 compared the graph with cheaper signals only side by side. Phase 7
tests the increment directly on Phase 5's 259 pairs, reading the 518 retained
graphs again. No sample, mutant or graph was made, and no GPU was used.
Pre-registered in `PREREGISTRATION_CLOSING.md`, written after a design panel and
three adversarial reviews. It is a second look at pairs that produced Phase 5's
leads, so a positive answer would have needed new problems.

**The blocks:**
- **C, the cheap baseline:** the kind of edit, plus the output distribution
  (code, edit-token and lowest log-probabilities, mean entropy, length in
  characters, the final position's top probability and entropy).
- **G:** the 49 graph features.
- **P, a probe of the same forward pass:** every active transcoder feature's
  activation, averaged over positions and reduced to 45 SVD directions, with no
  attribution.
- **L:** eight quantities at and just after the edited tokens, four from
  activations and four from attribution.

Each pair's survivor, and the passing source it was mutated from, was also
checked on Phase 6's extra inputs.

**Four of the five tests were withdrawn.** The pre-registered tests are clustered
conditional-independence tests (a GCM with a Rademacher max-|T|). On synthetic
labels over the real covariates, before any real label was read, they rejected
6–6.5% of true nulls at 5%, even for columns of pure noise, and up to 14% under
adversarial designs. By the pre-registered rule, the graph and local tests (and
graph size, β_5's lead) report T without a p. The comparison rests on
increments, corrected for the dilution that extra columns cause in a forest:

| within-pair accuracy | A | 95% CI |
|---|---|---|
| C, the kind of edit and the output distribution | 0.707 | [0.640, 0.771] |
| G, the 49 graph features (Phase 5's Ac) | 0.641 | [0.561, 0.716] |
| P, plain activations, no attribution | 0.685 | [0.614, 0.754] |
| G's three attribution-free features alone | 0.541 | [0.476, 0.604] |
| L, the edit's local quantities | 0.537 | [0.465, 0.608] |
| **G added to C**, corrected | **+0.002** | [−0.072, +0.074] |
| L added to C, corrected | −0.006 | [−0.056, +0.043] |
| G added to P, the active-feature count and the output distribution, corrected | +0.022 | [−0.040, +0.079] |

Adding the graph to C was negative in all ten refits with other seeds (−0.046
to −0.008). It was also negative:
- with the baseline first approved (no final-position columns: −0.044);
- with the tokens after the edit and the syntactic context added (−0.027);
- on the 93 pairs edited at the same token.

**The label.** A third of the survivors (64 of 193 checkable) pass MBPP's three
asserts but return a wrong value on a nearby input:

| signal | verified pairs (129) | lucky pairs (64) | verified − lucky |
|---|---|---|---|
| graph | 0.721 | 0.469 | +0.25 [+0.05, +0.44] |
| C | 0.806 | 0.609 | +0.20 [+0.01, +0.38] |
| probe | 0.787 | 0.594 | +0.19 [+0.03, +0.36] |

The graph, C and the probe rank the lucky pairs near chance. When neither member
of a pair is truly correct, they do not tell them apart, so they follow whether
the edit broke the program, not whether it passed the asserts. (The edit's local
quantities L are the exception: alone they rank the lucky pairs below chance,
0.375 [0.270, 0.492].) The label noise dilutes the signals alike and does not change the
increment.

**What it adds up to.** On these pairs, the attribution graph's summary is not
shown to know more than the kind of edit and the output distribution. A probe of
the same forward pass without attribution does as well. Inside the graph, the
attribution-dependent columns carry most of Phase 5's 0.64 (the three
attribution-free features alone reach 0.54; the difference, +0.100
[+0.000, +0.200], is undecided as published and above 0 without the erratum's
pair). Beyond C and the active-feature count they add nothing measurable (the one
valid test: p 0.024 against Holm's 0.0167). The interval of the graph added to C
does not exclude a gain of up to 0.07. The tests that would have settled it
could not be run at a valid size, and the pairs are not new.

## Phase 8: zeroing graph-ranked features at the model's own bugs

The paper's second claim (§4.4) is causal: zeroing one transcoder feature picked
from the graph fixed a bug (`high = mid`). It reports that one case, with no rate
and no control. Phase 8 measures the rate at Gemma's own one-token bugs, against
controls. Each site is a position in a failing solution from Phase 6 where Gemma's wrong token
was its top choice and a one-token repair is verified: it passes the asserts and
the calibrated extra inputs. At the decision position, the features ranked
highest for the wrong token's logit are zeroed, cumulatively, until the model's
top token changes (at most 1024). The new token is spliced in. Where that edit
was not among the judged mutants, the model completes the line under the same
ablation. The program is then judged blind. Pre-registered in
`PREREGISTRATION_P8_INTERVENTION.md` after a pilot on 30 sites from other
problems; the design is in `data/intervention_design/`.

**The arms:**
- **G:** the graph's ranking, by each feature's linearised effect on the wrong
  token's logit.
- **RND1 (S1):** for each of G's features, a random feature at the same layer
  and position, of similar size.
- **BAN (S2):** no ablation; forbid the wrong token and take the next one.
- **GxA (S3):** gradient × activation from one backward pass, without the graph.
- **Descriptive:**
  - four more random draws;
  - the graph's ranking on the log-probability (G_LP);
  - G's single top feature (G1);
  - middle layers only (G_mid);
  - direct effects only (DE);
  - features ordered by their measured single ablations (ORC);
  - a ranking that uses the repair (CONTRAST);
  - whole-program generation.

**Result: the graph's features beat random ones, but not the ban.** The analysis
covers 142 sites (92 distinct bugs, in 118 failing solutions) over 30 problems.
4 sites were excluded by a registered rule: there the model preferred the wrong
token by less than twice the noise floor (margins 0.06–0.15, against 2δ = 0.38).
Repair rates are equal-weight over problems:

| arm | repair rate | 95% CI | top token changed | median features zeroed (sites that flip) |
|---|---|---|---|---|
| BAN, forbid the wrong token | 0.561 | [0.404, 0.715] | 100% | — |
| G, the graph's ranking | 0.337 | [0.203, 0.481] | 91% | 20 |
| GxA, no graph | 0.395 | [0.256, 0.547] | 91% | 14 |
| RND1, matched random | 0.049 | [0.007, 0.125] | 10% | 264 |
| ORC, measured single ablations | 0.518 | [0.357, 0.673] | 92% | 4 |
| CONTRAST, uses the repair | 0.614 | [0.469, 0.756] | 87% | 9.5 |

| step | test | D | 95% CI | m | p | decision |
|---|---|---|---|---|---|---|
| S1 | G > RND1 | +0.287 | [+0.141, +0.441] | 15 | 0.0004 | rejected |
| S2 | G > BAN | −0.224 | [−0.369, −0.086] | 15 | 0.998 | not rejected |
| S3 | G > GxA | −0.059 | [−0.175, +0.041] | 9 | — | not tested |

**Why the graph loses to the ban.**
- When G's ablation changes the top token, the new token is the ban's in 70 of
  129 flips. Those flips give 48 of G's 57 repairs.
- In the other 59 flips the model moves to a token that is usually wrong (9
  repairs).
- So D(G − BAN) = −0.22 comes from breaks. At 39 sites G flips to a failing
  token where the ban's token passes. Only 7 sites are rescues. At 4 more the
  ban's token passes where G never flips (G does not flip at 13 sites in all).
- Gradient × activation, without the graph, does as well. Where both flip, it
  repairs 0.45 against G's 0.40.
- Ordering features by their measured single ablations does better than either
  (0.52).

**The paper's single feature (post hoc).** Zeroing one feature at a time, among
G's top 128 and gradient × activation's top 256 (about 320 distinct per site):
- changes the top token at 27 sites (19%); one of 128 random features, matched
  to G's top 128, does so at 5;
- yields a verified repair at 22 sites (15%), but at 20 of them the repair is
  the ban's token;
- gives a repair the ban does not give at only 2 sites.

**Side effects.** G's ablation also changes the model's top token at some later
position of the repaired program (teacher-forced) at 60% of sites (57% of the
129 where it flips). Random features ablated in the same number do so, in most
of 20 draws, at 9% of those 129 sites.

**Predictions.** Of 34 predictions written before any GPU data, 21 held; of 10
revised after the pilot (label-free), 9 held. The decisions held: S1 rejects, S2
does not, S3 is not reached. G's repair rate (0.34) and D(G − BAN) (−0.22) fell
below the original ranges, and inside the revised ones.

**What it adds up to.** The graph's ranking is not arbitrary: it finds features
whose removal changes the decision, where random features rarely do. But its
repairs are mostly the runner-up token, which forbidding the wrong token gives
for free, and where it moves the model elsewhere it mostly breaks the code. No
advantage over a single backward pass was found either. The phase used 21.55 of
its 28 GPU-h. Its limits:
- one-token substitutions at known sites;
- the wrong token's logit as the target;
- Gemma-2-2b-it with its transcoders;
- 30 MBPP problems in Rust.
